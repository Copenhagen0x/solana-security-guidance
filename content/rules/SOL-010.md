# SOL-010 · Reinit attack

A reinitialization that overwrites a live account — matched on the PROPERTY, not one idiom. Two forms: (1) Anchor `init_if_needed` on an account holding value/authority → a 2nd call reinits, dropping balances (and the same footgun enables nullifier/spent-marker double-spend: an `init_if_needed` nullifier PDA that doesn't abort on a pre-existing entry, or a spent-marker checked AFTER the transfer, lets one note redeem twice); (2) a hand-rolled reinit — a raw `.data.borrow_mut()` / `try_borrow_mut_data()` write of the account header with no `#[account(zero)]` / discriminator / `is_initialized` guard, so a caller re-inits a live account and overwrites its stored authority (the Metaplex Candy Machine v1 config-drain). `owner == program_id` proves ownership, NOT freshness. Fix: reject a re-init before the write (check discriminator).

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the reinit site — an init_if_needed account, OR a raw account-header write (.data.borrow_mut() / try_borrow_mut_data) — that holds value or authority (re-init drops/overwrites it).

**Do NOT flag when** — cite the number when suppressing a finding:

1. the account holds no lamports, token balances, authority keys, OR access-gating state that a second initialization could reset — access-gating state includes (non-exhaustively) a timestamp / nonce / status used as a lock, AND any field that controls subsequent PDA derivation, account creation, or role assignment
2. an explicit already-initialized guard REJECTS a second initialization before any write — for a hand-rolled `.data.borrow_mut()`/`try_borrow_mut_data` write the 8-byte discriminator is asserted all-zero (`data[0..8] == [0;8]`) or an `is_initialized`/version flag asserted false and the handler returns Err when already set (Orca `initialize_dynamic_tick_array`), for Anchor it is plain `init` / `#[account(zero)]`; a bare `.data.borrow_mut()` that only writes a data region of an already-type-validated account (discriminator/authority untouched) also clears this
3. the value-moving path is gated by a nullifier/spent-marker created with plain `init` so a duplicate redemption ABORTS AT ACCOUNT CREATION before any payout - NOT a mutable boolean flag in an existing account (a flag a reset/reinit path can re-open does NOT clear this rule)
