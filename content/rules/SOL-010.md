# SOL-010 · Reinit attack

`init_if_needed` on accounts holding value/authority → a 2nd call reinits, dropping balances; the same footgun enables nullifier/spent-marker double-spend (an `init_if_needed` nullifier PDA that doesn't abort on a pre-existing entry, or a spent-marker checked AFTER the transfer, lets one note redeem twice). Fix: plain `init` + an explicit existence guard, checked before any payout.

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the init_if_needed account that holds value or authority (re-init drops it).

**Do NOT flag when** — cite the number when suppressing a finding:

1. the account holds no lamports, token balances, authority keys, OR access-gating state that a second initialization could reset — access-gating state includes (non-exhaustively) a timestamp / nonce / status used as a lock, AND any field that controls subsequent PDA derivation, account creation, or role assignment
2. an explicit already-initialized guard rejects a second initialization
3. the value-moving path is gated by a nullifier/spent-marker created with plain `init` so a duplicate redemption ABORTS AT ACCOUNT CREATION before any payout - NOT a mutable boolean flag in an existing account (a flag a reset/reinit path can re-open does NOT clear this rule)
