# SOL-046 · Hand-rolled dispatch bypasses framework guards

A program routes instructions by hand (`match instruction_data[0]` / a native `entrypoint!` that splits the tag byte) instead of Anchor's `#[program]` macro, so NONE of Anchor's auto-generated guards run - no 8-byte discriminator, none of the `#[account(...)]` constraints (`has_one`/`seeds`/`owner`/`signer`/`mut`) - because that code is only emitted for `#[derive(Accounts)]` handlers. Accounts arrive as a bare `&[AccountInfo]`; wrong-type/owner/unsigned/substituted accounts sail through at once. Distinct from SOL-019 (Anchor present, one missing discriminator). Fix: route through `#[program]` + `#[derive(Accounts)]`, or manually re-validate every account on every native arm (discriminator, owner, PDA, signer)

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the native entrypoint / hand-rolled dispatcher (match on instruction_data[0] or a split-first tag byte) that routes to a handler taking a bare &[AccountInfo] slice, where the routed handler then reads/mutates an account without re-deriving the discriminator, owner, PDA (canonical-bump compare), or signer that Anchor's #[derive(Accounts)] would have enforced.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the dispatched handler is an Anchor `#[derive(Accounts)]` context (the accounts arrive as a typed `Context<T>` whose struct carries the relevant `Account<'info,_>` / `Signer<>` / `has_one` / `seeds`+`bump` / `owner` constraints) — i.e. the hand-rolled `match` only selects an Anchor handler and does NOT itself consume a raw `&[AccountInfo]`; Anchor's generated guards still run
2. this IS a deliberate native (non-Anchor) program AND every account on the matched arm is manually re-validated before use — a positive 'all four guards present on THIS arm' proof, not 'the program looks careful': (a) the 8-byte discriminator is verified via `try_deserialize` (NOT `try_deserialize_unchecked`) or an explicit constant-tag compare; (b) `owner == program_id` (or the expected program) is asserted on each account whose data is trusted; (c) each claimed PDA is re-derived via `find_program_address` and the returned CANONICAL bump is compared against the account's STORED bump (SOL-016) — re-derivation via `create_program_address` with a CALLER-SUPPLIED bump does NOT count, because it accepts any valid off-curve bump and re-introduces the non-canonical-bump bug; and (d) `is_signer` is checked on every privileged/authority account
3. the byte-match is not an instruction dispatcher at all — it is a bounded enum/version-tag parse on already-program-owned, discriminator-validated data (e.g. matching a state-machine status byte read out of an `Account<'info,T>` whose owner and discriminator Anchor already checked), so no account validation is being skipped
4. the matched first byte selects only among handlers that take ZERO accounts (pure compute / read-only view that returns data WITHOUT reading, writing, moving lamports from, or CPI-ing through any passed account) — so there is no account whose owner/signer/PDA/discriminator could be forged. NOTE: a 'view' that READS even one passed account is NOT covered — it must still validate that account's owner and discriminator before trusting the data it returns
