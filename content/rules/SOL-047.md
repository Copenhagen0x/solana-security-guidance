# SOL-047 · Forged receipt token / mint

A redeem/burn/claim path accepts a caller-supplied receipt `Mint` or share token account and burns it for the underlying asset without asserting it is the mint the deposit path produced -> the attacker passes a mint they control, mints themselves a balance, and the program treats those worthless tokens as genuine shares, draining the vault. Distinct from SOL-007 (owner) and SOL-015 (generic missing constraint). Fix: pin the receipt mint to the stored canonical mint (`address = vault.receipt_mint`) AND bind the burned account's `token::mint`

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the redeem/burn/claim handler that reads a caller-supplied receipt Mint or share token account and pays out the underlying asset (CPI transfer / lamport credit) without that mint being asserted == the vault-stored receipt mint AND the burned token account bound to it; the cited call-site must show an attacker-substitutable mint/share-account reaching the burn or payout, not merely an unpinned Mint arg in an init/mint-authority context.

**Do NOT flag when** — cite the number when suppressing a finding:

1. The receipt mint is pinned to the deposit-produced mint stored in program state -- Anchor `address = <vault>.receipt_mint` or an explicit `require_keys_eq!(receipt_mint.key(), vault.receipt_mint)` before any burn or payout -- AND the burned share token account carries `token::mint = receipt_mint` (or its `.mint` is asserted == that pinned mint). BOTH bindings are required: pinning only the Mint arg while the share token account's mint is unchecked (or vice-versa) is still exploitable and is NOT cleared by this exclusion -- it is the incomplete-fix variant.
2. The share token account is a typed Anchor `Account<'info, TokenAccount>` whose `token::mint` / `associated_token::mint` is constrained to a mint that is itself program-derived or stored-in-state (not a caller-passed Mint), so the (mint, balance) pair cannot be forged. NOTE: this clears only the forgery/identity concern; it says nothing about whether the redeemed AMOUNT is then computed safely -- a perfectly pinned mint can still over-pay via a bad exchange rate or unbounded amount. That residual is the share-accounting class (out of scope for SOL-047); clear the SOL-047 identity finding here, but do not infer the redeem path is fully safe.
3. This is a one-mint protocol where the receipt mint is a hardcoded constant, or a fixed PDA `seeds = [b"receipt", vault.key().as_ref()]` re-derived in the same instruction (not read from a caller account), AND that canonical mint's `mint_authority` is the program/vault PDA (verified at init) so supply cannot be inflated by an external authority. A fixed/pinned mint *pubkey* whose mint authority is an outside key does NOT qualify -- the attacker mints unlimited genuine receipt tokens against a real mint, which is still SOL-047.
4. The redeemed amount is computed solely from program-stored per-user accounting (a position/receipt PDA owned by this program and bound by has_one/seeds to the caller) and the receipt mint/share token account is used only as an identity tag that is itself pinned per exclusion #1 -- the payout reads the recorded position, never a caller-supplied token balance or a caller-supplied amount. (If instead the handler pays out a caller-passed `shares`/`amount` arg or a caller-supplied token balance, this exclusion does NOT apply -- that is the unbounded-amount design exclusion #2 warns about, separate from the identity bug but not cleared here.)
