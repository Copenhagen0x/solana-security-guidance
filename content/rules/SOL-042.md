# SOL-042 · Unbounded account-iteration compute DoS

An instruction loops over a caller-controlled collection (`remaining_accounts`, a user-grown `Vec`/list) with no per-call length cap, so work scales until the tx exceeds the ~1.4M compute-unit ceiling and EVERY call reverts - permanently bricking the instruction (and any crank/settlement behind it). Cheap-to-grow, expensive-to-process is the lever. Distinct from SOL-027 (validates each account's identity, not the count). Fix: `require!(list.len() <= MAX)` with MAX proven to fit the CU budget, or paginate across txns with a stored cursor

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — medium.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the loop/iterator whose trip count is bound to an attacker-influenced length (ctx.remaining_accounts.len(), a Vec/map field a user can grow, or an append-only/admin-grown global list) with no per-instruction cap enforced before it. The regex matches both single-var and tuple-binding `for` loops (`for acc in …` and `for (i, acc) in remaining_accounts.iter().enumerate()`); it still misses non-`for` shapes: `while i < …len()` index loops and `.iter().for_each/map/fold(…)` chains.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the iteration is bounded by an enforced per-instruction cap BEFORE the loop (require!(list.len() <= MAX) / a fixed-size slice / .take(MAX) over a *validated* length / a `[T; N]` array) where MAX is a constant proven to fit the CU budget for this loop body — NOT an unverified 'it's usually small' assumption. HUMAN-VERIFY (RE2 cannot see this): the cap must not be a `.take()`/truncating slice that silently DROPS unprocessed entries when correctness requires all of them (e.g. a settlement/payout set) — that is a correctness bug masquerading as a fix; paginate instead. A truncating cap only qualifies when dropping the tail is provably correct for this handler.
2. the collection is append-only or growable but its GROWTH path is itself capped so it can never exceed the executable CU bound — a bounded `Vec`/`require!` at *every* push/realloc site, with the cited push site actually shown to be bounded. HUMAN-VERIFY (machine cannot prove a negative across the codebase): 'growth is probably bounded somewhere' is NOT a dismissal — name the file+line of the push site and show the cap there. A cap on the read/loop while the stored list can still grow unbounded does NOT qualify (a near-max list plus one more entry can still tip a *different* reader over).
3. the loop length is fixed by program state that can NEVER exceed the executable CU bound — a compile-time constant, a `[T; N]` array, or a count derived from validated PDAs the program itself created under a bounded scheme. NOTE: 'only an admin/Signer can grow it' does NOT by itself qualify — an admin (or a compromised/buggy admin path) that grows an append-only list past the CU bound bricks the instruction for everyone; the test is 'length is bounded by a CU-provable cap', not 'an attacker can't influence the length'. Prove the bound by tracing every write site, not 'this list looks internal'.
4. work is explicitly paginated / chunked across transactions with a persisted cursor (or an offset+limit argument) so no single instruction processes more than a bounded slice, the cursor cannot be reset to replay or skip work, AND — when the loop credits/pays/settles accounts — each iterated account is bound by identity to authoritative program state at the cursor offset (require_keys_eq! against a stored registry/PDA per index), so the cursor SELECTS recipients rather than merely counting iterations. A count cap + bare cursor that pays whatever the caller passes does NOT qualify — that is a double-pay/skip fund-drain (SOL-027), strictly worse than the DoS, and is NOT excluded by this rule.
