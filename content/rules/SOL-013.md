# SOL-013 · Token Program ID confusion

Hardcoded SPL Token ID but the account is Token-2022 (or vice versa). Fix: `anchor_spl::token::ID` via typed accounts; never hardcode.

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the hardcoded token-program id and the token account it is used to invoke.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the typed anchor_spl::token::ID / token_2022::ID is used via a typed Program<> account, not a raw literal
2. the literal lives only in a test/const and is NEVER reached on any runtime branch for a program id used in a CPI — including behind a #[cfg(feature = ...)] / #[cfg(not(test))] block that ships in ANY production build (verify the call site AND the build's enabled features, not just the declaration; only #[cfg(test)] truly excludes it)
