# SOL-045 · Incremental Merkle insertion error

An incrementally-maintained Merkle tree (SPL account-compression `ConcurrentMerkleTree`, Bubblegum cNFTs, or a hand-rolled filled-subtrees/changelog) updates its root from cached state instead of a full recompute. A wrong incremental update for some insert/replace sequence (off-by-one height, stale reused sibling, mismatched empty-node hash, wrong path direction, out-of-order changelog) diverges from the canonical root -> a forged-leaf proof validates or a real leaf is silently dropped. Distinct from SOL-008 (the account is the right tree; its root is wrong). Fix: delegate root maintenance AND proof verification to spl-account-compression via CPI (pin `merkle_tree.owner`); else differential-test the tree

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the append / set_leaf / replace_leaf (or hand-rolled compute_root over filled_subtrees / changelog) call site that updates the stored root, AND the verify_leaf / proof-check instruction that later validates a proof against that root — exploitability is confirmed when a proof for a never-inserted leaf rehashes to the stored root, or an inserted leaf's proof fails against it. Both sites must be cited: a correct mutation paired with a verify path that trusts a caller-supplied or stale root is still exploitable, and a correct verify paired with a divergent incremental root is still exploitable.

**Do NOT flag when** — cite the number when suppressing a finding:

1. ALL root maintenance AND all proof verification are delegated to the audited spl-account-compression program via CPI (append / replace_leaf / verify_leaf) and the handler only marshals accounts — delegating only the mutation (append/replace_leaf) while hand-rolling or trusting a caller-supplied root in the proof-verifying instruction does NOT clear the finding (the verify path is half the vuln class). The merkle_tree account passed into the CPI must additionally be pinned to spl_account_compression::ID via an Anchor `owner = …` constraint or a runtime require_keys_eq! on merkle_tree.owner (UncheckedAccount + has_one does NOT bind the tree authority — the account is never deserialized). A local copy/fork of the crate that has been MODIFIED does NOT qualify and must be re-audited.
2. FOR A HAND-ROLLED TREE, the following three conditions must ALL hold together (they are conjunctive, not independent OR-satisfiers; clearing on any one alone leaves the other half of the class open): (a) a differential test proves the incremental root equals a full bottom-up recomputation over RANDOMIZED insert AND replace sequences spanning multiple tree depths, the buffer-wraparound boundary, AND out-of-order / concurrent changelog consumption (the distinguishing failure mode of a ConcurrentMerkleTree vs a plain one — a test that only does sequential append/replace can pass while the concurrency path stays broken); a single happy-path append or a fixed hardcoded-sequence test is NOT sufficient — cite the test; AND (b) the empty/default node hash used at each level is the protocol-fixed constant identical to the one the full recompute uses, AND leaf-index path direction is derived from the canonical bit decomposition of the index (not an unverified 'sibling on the left/right' assumption), both verified against the recompute rather than a 'looks symmetric' read; AND (c) every proof-verifying instruction rehashes the supplied proof up to and compares against the STORED on-chain root using the leaf index's path direction — NOT a caller-supplied root, a cached/changelog root that may be stale, or a root read from an unvalidated account.
3. the instruction is read-only with respect to the tree (no append/set_leaf/replace_leaf/compute_root mutation site AND no proof-verifying/inclusion-check site is present in the reviewed path) — the divergence class requires at least one of the two sites to be reachable, so a handler that neither mutates the root nor verifies a proof against it is out of scope
