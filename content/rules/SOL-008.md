# SOL-008 · Unverified PDA

PDA used without `find_program_address` validation → attacker passes any account as the PDA. Fix: derive and compare.

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the use of a PDA account that is never re-derived and compared via find_program_address.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the address is re-derived via find_program_address and compared, or Anchor seeds = [...] + a canonical `bump` constraint enforce it (a `bump = <stored_field>` counts ONLY if that stored bump itself passed SOL-016 canonical-bump validation; has_one alone does NOT verify canonical PDA derivation and is not sufficient by itself; and if an Anchor `seeds::program = <id>` is used, that <id> must be a hardcoded/trusted program id, NOT an attacker-supplied or runtime-mutable value — including a field loaded from ANY account (even a typed Account<>) unless that field is a compile-time constant or was set by a verified admin and cannot be changed by non-admin callers)
