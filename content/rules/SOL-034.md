# SOL-034 · Manual lamport mutation

Direct lamport writes (`try_borrow_mut_lamports`) without the matching debit/credit → funds conjured/burned vs program accounting. Fix: mutate both sides; assert conservation.

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the manual lamport write and the internal balance/claim field it must stay in sync with.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the mutation updates BOTH the lamports and the matching internal balance/claim field in the same instruction (cite both writes), and the debited account remains rent-exempt afterwards
2. the mutation is the documented rent-refund path of an account close: the destination is validated against stored state (not caller-chosen), and the account's data is zeroed or discarded in the same instruction
3. the accounts are system-owned and the movement uses a system-program transfer CPI — a manual write on a system-owned account cannot deduct anyway (the runtime rejects it); flag it as dead/misleading code
