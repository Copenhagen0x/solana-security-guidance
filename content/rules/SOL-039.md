# SOL-039 · Asymmetric partial-CPI state

A handler mutates its OWN accounts (records a withdrawal, clears a debt, burns shares) then fires a fund-moving CPI whose `Result` is SWALLOWED (`let _ =`, `.ok()`, `.unwrap_or*`, a logged `.is_err()`, or a `match`/`if let Err` arm that does not re-`?`). On Solana only an `Err` returned from the top-level instruction reverts account writes, so a caught inner-CPI failure leaves the outer mutation committed while no tokens moved -> the attacker farms one-sided state by forcing the CPI to fail. Distinct from SOL-033 (stale read after a successful CPI). Fix: propagate the CPI with `?` so the whole instruction reverts; if you must catch the error, roll back every prior self-mutation

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the inner fund-moving CPI call site whose Result is discarded (let _ =, .ok(), .is_err()/.is_ok() logged-and-ignored, .unwrap_or*, or a match/if-let-Err arm that does not re-?) inside a handler that has already written one of its own program-owned accounts before that CPI.

**Do NOT flag when** — cite the number when suppressing a finding:

1. The swallowed call is not a fund-moving CPI — a local helper, msg!, or checked-arith Result with no external/cross-account effect. Confirm the discarded Result belongs to an invoke/invoke_signed or token:: CPI, not an unrelated value.
2. The CPI is actually `?`-propagated or `.map_err(..)?`'d — the instruction reverts on failure, so there is no asymmetry. (The regex does not fire on a bare `?`/`.map_err(..)?` call; cite this only if a reviewer mis-reads a propagated call.) This also covers a `match`/`if let Err(e) =` whose arm `return Err(e)`s or `?`-propagates - the instruction still reverts, so there is no asymmetry even though the regex fires on the `match`/`if let` head.
3. The discarded Result feeds a `require!` / `assert!` / `ensure!` (e.g. `require!(token::transfer(..).is_ok(), E)`): this RETURNS Err on failure and reverts the whole instruction, so it is SAFE. The regex FIRES on every `require!`/`assert!`/`ensure!`-guarded `.is_ok()` (it is lookbehind-free / RE2-compatible) - cite this exclusion to dismiss them; they are safe because the macro returns Err on failure and reverts the instruction.
4. The catch branch (`.ok()` consequence, the `Err(..)` match arm, the `if let Err` body) FULLY rolls back every prior self-mutation before returning — re-credits the debt, un-burns the shares, restores the nonce — so committed state stays symmetric on failure.
5. No program-owned account is written before AND the swallow leaves no attacker-controllable asymmetry — i.e. the CPI is the handler's only state change, OR the only prior writes are idempotent set-to-constant values that a replay/retry re-derives identically (nothing the attacker can farm by forcing the CPI to fail). NOTE: cite this even when an UNRELATED write follows the CPI later in the handler — the gate is 'was a dependent self-mutation committed before the swallow that a failed CPI would orphan', not 'is the CPI the literal last statement'.
