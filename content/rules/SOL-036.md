# SOL-036 · ATA derivation unpinned

A token account is trusted as "the user's ATA" without verifying it's the canonical ATA for (owner, mint) → attacker passes a different token account they control, redirecting deposits/payouts. Fix: Anchor `associated_token::mint` + `associated_token::authority` constraints, or compare against `get_associated_token_address(owner, mint)` (owner+mint from validated on-chain state, not caller data) before use.

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the token account trusted as a specific owner's ATA without a canonical-derivation check.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the account carries Anchor `associated_token::mint = <mint>` AND `associated_token::authority = <owner>` constraints (Anchor re-derives and enforces the canonical ATA)
2. the account key is compared against `get_associated_token_address(owner, mint)` (or the Token-2022 variant for the actual token program) before any deposit/payout, with owner and mint both sourced from validated on-chain state — NOT from caller-supplied instruction data
3. the token account is a program-owned vault pinned by a PDA seed/has_one (not a per-user ATA at all), so canonical-ATA derivation does not apply
