# SOL-044 · Hardcoded slot-time rate

Interest/emissions/vesting/funding accrual computed from a hardcoded slot->time conversion (a `SLOTS_PER_YEAR` constant, or a slot delta scaled by an assumed ~400ms/slot) instead of `Clock::get()?.unix_timestamp`. Solana slot time is not constant (it drifts, historically slower), so accrual silently diverges from wall-clock -> compounding over/under-payment an attacker farms around known slow/fast periods. Distinct from SOL-001 (trusting a caller-supplied slot). Fix: accrue on `Clock::get()?.unix_timestamp` deltas (store `last_update_ts`), never a hardcoded slots-per-period constant

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — medium.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the accrual/rate computation (interest, emissions, vesting, funding) that converts a slot count or slot delta to elapsed time via a hardcoded slots-per-period or ms-per-slot constant instead of reading Clock::get()?.unix_timestamp.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the elapsed time driving the accrual is computed from Clock::get()?.unix_timestamp deltas (e.g. now_ts - last_update_ts on stored i64 timestamps), and the slots-per-period / ms-per-slot constant is used only for a non-economic, non-priority purpose such as log formatting or a UI hint that never scales a payout and never decides ordering/fill/liquidation/seniority — naming which it is
2. the hardcoded constant is NOT a slot→time conversion at all — name what it actually is (a compute-unit budget, a bps/percentage denominator, a fixed-point Q-scale, a seeds/byte-length constant, or a per-slot reward that is intentionally denominated in slots by spec with the slot-denomination cited) — so no wall-clock assumption is embedded
3. the protocol is provably slot-denominated by design: cite the spec clause that defines the rate per SLOT rather than per unit of real time, AND trace every consumer of the slot-accrued field to confirm none compares, sums, or mixes it with a unix_timestamp-derived value (any such mix reintroduces the drift; this is an explicit trace of all readers, not a glance)
4. the slot delta is converted to time only to form an UPPER/LOWER bound in a conservative safety check, AND the citer states (a) the comparison sign and (b) the worst-case drift direction (slots historically run SLOWER than 400ms → the same slot delta spans MORE wall-clock), and shows that under that drift the check can only ever REJECT more than wall-clock would (stricter), never ACCEPT more value than real time allows — a max-staleness gate `now_slot - last_slot < MAX` is NOT covered, because slow slots make it accept quotes that are actually staler than intended
