# SOL-033 · Stale account read after CPI

An account field read after a CPI that can mutate it (or cached from before) → decisions on stale balance/authority. Fix: `reload()` / re-read after the CPI.

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the post-CPI read site and the CPI that can mutate the account it reads.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the account is reload()ed (or re-deserialized from its AccountInfo) between the CPI and the read
2. the callee provably cannot mutate the read account — it is not in the CPI's account set and the callee cannot reach it via nested CPI (name the callee and its full account set; 'the callee looks unrelated' is NOT sufficient)
3. the read value feeds only logs/events, never a gate, an amount computation, or stored state
