# SOL-051 · Predictable on-chain entropy

A value-bearing draw (lottery winner, NFT trait roll, raffle, randomized ordering, airdrop pick) is seeded from on-chain-observable values - `Clock` `unix_timestamp`/`slot`, the `RecentBlockhashes`/`SlotHashes` sysvar, or any field readable before the tx lands - so it is not secret: the submitter simulates and only sends when they win (grinds it), and the slot leader can steer the slot/blockhash -> the prize is deterministically claimable. Distinct from SOL-001 (trusting a caller-supplied slot for auth; here the slot is honest but misused as randomness). Fix: use a VRF (Switchboard/ORAO) or a real commit-reveal; owner-check the oracle result account and bind it to this draw

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the instruction that selects a winner / rolls a trait / picks an ordering and reads Clock unix_timestamp/slot, the RecentBlockhashes or SlotHashes sysvar, or another pre-tx-observable value as the seed, then writes a value-bearing result (payout, mint, rank) from it — confirm the modulo/reduction result is read by the value-bearing decision, not by a cooldown/rate-limit/epoch-index path.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the randomness comes from a VRF whose ORACLE-OWNED result account is verified before use — you assert `*acct.owner == <switchboard/orao program id>` (or use the oracle's typed wrapper that enforces it) AND parse it with the oracle's type (e.g. Switchboard `RandomnessAccountData::parse`), AND that result account is bound to THIS specific draw by a key recorded at request/commit time (`has_one`, or comparison against a `Pubkey` stored in your state) — a VRF whose result account is read but never owner-checked, OR bound only via a `seeds=[…, pool.key()]` PDA re-derived under YOUR program id (which can never point at a genuine oracle account and is itself attacker-writable), is NOT sufficient
2. the value is read through the oracle's reveal method that FAILS when the round is not yet fulfilled (e.g. `RandomnessAccountData::get_value(clock.slot)` returning `RandomnessNotResolved`) and a zeroed/unrevealed buffer is rejected — a self-set `fulfilled`/`settled` bool on a program-local account, or reading the buffer before fulfillment, does NOT qualify, AND the request is fresh (the committed `seed_slot`/commit slot is checked so a stale or expired round cannot be replayed)
3. the draw uses a commit–reveal where the committed value is stored on-chain BEFORE the seed material becomes knowable and the reveal is checked against the commitment (hash preimage) — a 'commit' that commits to a value the committer can still grind at reveal time does NOT qualify
4. the timestamp/slot feeds time-bucketing, a cooldown or rate-limit window, or expiry math (`now % period`, `slot % epoch_len` as an epoch/round index), NOT a value-bearing draw outcome — proven by tracing that no payout, mint, rank, or fund-routing decision reads the modulo result (this is the single most common legitimate use of `unix_timestamp %` / `slot % len` and is the primary false-positive class on the timestamp/slot regex arms)
5. the on-chain value (timestamp/slot/blockhash/key) feeds a NON-value-bearing, non-adversarial use only — a UI tiebreaker, a non-prize display shuffle, or jitter on a value no party profits from steering — proven by tracing that no payout, mint, rank, or fund-routing decision reads the result (a positive 'no value rides on this draw' proof, not 'looks cosmetic')
6. the value is used as a uniqueness/nonce or PDA seed, NOT as the random outcome itself (predictability is fine for a nonce; the draw result must not be a function of it)

## Real exploits in this class

No publicly catalogued exploit in the [Hacks Database](../../hacks/README.md) maps to this class yet. The rule is drawn from documented Solana audit patterns, not a specific in-the-wild loss.
