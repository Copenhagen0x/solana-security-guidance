# SOL-018 · Hardcoded System Program ID

`"111…"` literal instead of the imported constant. Fix: `solana_program::system_program::ID`.

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — LOW.** LOW — hygiene / defense-in-depth / operational (filtered out by `--min-tier high`)

**Baseline severity — low.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the 32-ones System Program literal used instead of system_program::ID.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the program-id comparison uses the imported system_program::ID type-safely, not a raw string literal
2. the literal appears only in a #[cfg(test)] module or a const that is never reached on a runtime program-id verification — a #[cfg(feature = ...)] block that ships in a production build does NOT qualify

## Real exploits in this class

No publicly catalogued exploit in the [Hacks Database](../../hacks/README.md) maps to this class yet. The rule is drawn from documented Solana audit patterns, not a specific in-the-wild loss.
