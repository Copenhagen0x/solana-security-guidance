# SOL-050 · Serialization symmetry mismatch

The bytes written for an account and the bytes read back come from two DIFFERENT layouts - write `u64`/read `u32`, a reordered struct field, a second hand-written reader, a `#[repr(Rust)]` zero-copy struct the compiler may reorder, or a hand-computed offset off by N - so the loaded value is not the stored value, silently corrupting a `balance`/`authority`/`bump`; an attacker tunes the bytes at the disagreeing offset. Distinct from SOL-017/025 (an unverified raw deserialize; this survives a fully-typed, owner-checked one). Fix: pack and unpack through ONE shared (de)serializer over the same type; guard with a `size_of` tripwire + a `unpack(pack(x)) == x` test

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the read/deserialize site whose field widths, field order, or byte offsets disagree with the write/serialize site for the same account (the loaded value differs from what was stored), including a second hand-written reader (`from_le_bytes` / manual offset) that parallels — and drifts from — a typed write, or two programs that each use their OWN copy of a "same" type that has diverged.

**Do NOT flag when** — cite the number when suppressing a finding:

1. BOTH the write and read side go through ONE shared (de)serializer over the SAME type DEFINITION (same struct in the same crate/version, not just "a derived codec on each side") — one Anchor `#[account]` type, one `#[derive(BorshSerialize, BorshDeserialize)]` struct, or one `#[repr(C)]` `bytemuck::Pod` struct loaded via `AccountLoader` on BOTH sides — with NO hand-written byte slicing / `from_le_bytes` / manual offset on either side. A duplicated type copied into a second program/module that may have drifted does NOT qualify: the two definitions must be the literal same source (shared crate dependency), because two independently-edited "Vault" types each using their own derive can still disagree on width/order.
2. the layout is a zero-copy / Pod struct that is `#[repr(C)]` (or `#[repr(C, packed)]`) AND is loaded through that one Pod type via `AccountLoader` on BOTH the write and read side (symmetric by construction). A `const_assert_eq!(size_of::<T>(), N)` is REQUIRED additionally as a width/field-count tripwire, but is NOT sufficient on its own to dismiss a flag: `size_of` is a single scalar, so a same-size field REORDER passes the assertion unchanged. A bare `#[derive(Pod)]` on a default `#[repr(Rust)]` struct (compiler may reorder) also does NOT qualify.
3. both the write and read go through one manual offset/width defined ONCE as shared named constants (`const BAL_OFF`, `const BAL_LEN`) referenced by both sides AND covered by a round-trip property test that asserts `unpack(pack(x)) == x` over the field's full range — a single happy-path encode/decode is NOT sufficient.
4. the disagreeing value is a temporary that is decoded and fully consumed WITHIN the same function (never stored back to an account, returned, emitted, or read by any later authority/accounting gate) — a locally-scoped, locally-checkable non-persistence, NOT a whole-program "never used downstream" claim (which is not verifiable at a single write/read site and should not be asserted).
