# SOL-043 · Unbounded storage / slot-exhaustion griefing

A permissionless instruction lets an attacker consume an unbounded share of a persistent SHARED resource - a monotonic global registry/list, program-subsidized account growth, or front-running the init of a depended-on singleton - denying state every other user relies on. Distinct from SOL-012 (rent funding): here growth is attacker-driven and one-way. Fix: per-caller fixed-size caller-paid PDAs, or a self-limiting shared cap (decrement-on-close + a refundable stake); admin-gate close

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the permissionless instruction handler that (a) appends a caller-controlled entry to a persistent shared account / grows it via realloc/init_if_needed with no cap, (b) gates registration behind a shared monotonic counter that only increments and is never decremented on close, or (c) closes / front-runs the init of a singleton PDA other instructions depend on — with no per-caller scoping, no caller-funded rent, no slot-release/deposit, and no admin gate.

**Do NOT flag when** — cite the number when suppressing a finding:

1. per-caller data lives in ONE fixed-size PDA seeded by the principal's own key (seeds = [..., caller.key().as_ref()], one account per caller, no shared growable list) AND rent is paid by that caller (payer = caller) — so a single attacker can inflate only their own rent-paid account and cannot enlarge shared state or evict others. This is the preferred shape; a shared global cap is NOT required when each caller is isolated this way.
2. where a SHARED cap is used, it is genuinely self-limiting: the slot count is DECREMENTED in a close/deregister handler so closing an entry frees a slot, AND/OR each registration requires a refundable deposit/stake that makes N throwaway-key Sybils economically prohibitive. A monotonic `require!(count < MAX_ENTRIES)` over a counter that only ever increments (never decremented on close) is NOT sufficient — that is itself a permissionless global-exhaustion DoS (the SOL-022 write-only-counter pattern) and does NOT clear this rule, even though total size is bounded; 'size bounded' is not 'service available'.
3. each appended slot's incremental rent is paid by the CALLER themselves (payer = caller, or a system-program transfer in the SAME instruction) — growth is self-limiting and the program/treasury never subsidizes it; a program-funded or PDA-funded grow (realloc::payer = vault/program) is NOT sufficient.
4. the close / lifecycle-transition of the depended-on PDA is gated by a Signer<> bound by constraint to a hardcoded or program-stored admin/authority key (close = admin with has_one = admin WHERE admin is declared Signer<>, or constraint = signer.key() == config.admin) — a bare Signer<> the caller self-assigns, a has_one on a NON-signer account, or a `close` reachable by any caller, is NOT sufficient.
5. the singleton PDA exposed to an init-front-run is seeded by a FIXED or admin-controlled key (not caller-supplied data), is created at deploy time, OR its init is idempotent (re-init is a no-op / verifies the existing state belongs to the program) — so an attacker cannot pre-create it with hostile state or block legitimate creation. A permissionless `init`/`init_if_needed` of a depended-on singleton whose seeds an attacker can satisfy first is NOT sufficient.
