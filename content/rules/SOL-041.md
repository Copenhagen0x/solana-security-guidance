# SOL-041 · Forced-balance / supply desync

A raw on-chain balance - an account's `lamports()` or a token account's `amount` - is read as the AUTHORITATIVE internal supply/reserve driving a price/share/payout. Anyone can force-add balance the program never accounted for (a direct transfer, rent top-up, or pre-funded init before the program runs), inflating that total with no matching ledger entry -> desynced invariants, excess shares minted, pool drained (the SafeMoon reflection class). Distinct from SOL-011/034 (which write lamports out of sync). Fix: drive math from a program-owned recorded ledger updated by measured deltas; read the raw balance only to assert `live >= recorded`

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the price/share/payout computation that reads a raw vault `lamports()` or token-account `amount` (or the absolute post-CPI balance) as the supply/reserve total, plus the permissionless balance-inflation path — a plain SPL/SystemProgram transfer into that vault, a Token-2022 fee/interest credit, OR a pre-existing balance seeded before the instruction runs (front-run init / prior-slot transfer / rent top-up) — that lets an attacker move the "total" without a matching ledger write.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the supply/reserve total driving the calculation is a program-owned stored ledger field (e.g. `state.recorded_reserve` / `state.recorded_shares`) that is mutated ONLY inside accounted deposit/withdraw/skim handlers by a MEASURED balance-delta (snapshot before, `reload()` after the CPI per SOL-033, credit `after − before` with `checked_*` per SOL-014 — never the requested `amount_in`), and the live `lamports()` / token `amount` is read for at most a solvency assertion (e.g. require live >= recorded), never as the value fed into the price/share/payout math
2. the raw balance is read only to GATE solvency (require `vault.amount >= owed`) or for display/logging, and is provably never used as a divisor, multiplier, or supply input to mint shares / set a price / size a payout (trace every use-site to a concrete non-pricing sink — a 'looks like a balance check' claim is not sufficient)
3. the vault is a per-trade escrow whose entire balance is created and consumed within ONE instruction by the program itself AND the read uses the in-instruction balance-DELTA it credited (snapshot-before / `reload()` / `after − before`), NOT the absolute `vault.amount` — on Solana a vault/escrow PDA can be pre-funded by anyone before the instruction ever executes (front-run init, prior-slot transfer, rent top-up), so an absolute-balance read is NOT made safe merely by being single-instruction
4. a donated surplus is reconciled only by an admin-gated skim instruction that the caller must SIGN AND that is bound by constraint to a hardcoded/program-stored admin key, that updates `recorded_reserve` (and `recorded_shares` if applicable) atomically with the tokens it moves so the solvency invariant still holds afterward, and the share/price math still derives from the stored ledger rather than the post-skim live balance
5. the pool is protected against first-depositor inflation independently of this read — minimum-liquidity dead shares are locked on seed (or a virtual-reserve/virtual-share offset is used) AND dust deposits that round to zero shares are rejected (`require!(shares > 0)`) — so even a handler that later moves reserve independently of shares cannot be gamed into a 1-share pool
