# SOL-052 · Token-2022 semantics assumed

Code that accepts a Token-2022 mint but assumes classic SPL-Token behavior: it credits the requested (not received) amount, or never handles extensions - transfer-fee skims a cut so the vault receives less than booked, a transfer-hook runs attacker code mid-CPI, non-transferable / default-frozen silently breaks a transfer or locks a deposit -> vault under-collateralized or shares minted against tokens that never arrived. Distinct from SOL-013 (which program id) and SOL-032 (decimals). Fix: pin classic `Program<Token>` on every token CPI, or measure the received delta and reject unsupported Token-2022 extensions before value moves

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the token-handling path that accepts a generic InterfaceAccount / possibly-Token-2022 mint and assumes classic SPL behavior - crediting the requested (not received) amount, or moving value without checking for TransferFee / TransferHook / NonTransferable / DefaultAccountState(Frozen) / PermanentDelegate extensions.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the program is hardwired to classic SPL Token via a typed Program<'info, Token> (anchor_spl::token::ID) on EVERY token CPI (not just the deposit path) AND the mint is constrained so a Token-2022 mint can never enter the handler - Token-2022 extensions cannot apply to a mint the classic Token program owns
2. the mint's extensions are explicitly enumerated via StateWithExtensions / get_extension_types() and every UNSUPPORTED one is REJECTED before any value moves - TransferHook, NonTransferable, DefaultAccountState(Frozen), PermanentDelegate - and TransferFeeConfig is HANDLED via a payer-side measured delta (NOT merely absent from the reject set); a Program<Token2022> pin or a 'we only list vanilla mints' comment is NOT sufficient, and account-level extensions on the touched ATAs (CpiGuard, TransferFeeAmount) are inspected too
3. the received amount is the PAYER-side measured delta (the user's source ATA before-minus-after, or a fresh per-deposit escrow ATA no other party can pay into), so a transfer-fee skim cannot over-credit, AND the destination token account is bound to the vault by Anchor constraints (token::mint + token::authority) so a substituted or worthless-mint account cannot be passed
4. the token only ever leaves the program (one-way payout to a user-chosen account) and is never re-credited to internal accounting nor used to mint shares, so a fee skim or transfer-hook cannot create an internal-vs-actual imbalance
