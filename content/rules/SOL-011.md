# SOL-011 · Lamport drain via close

`close =` on an account not fully drained, or a close that doesn't zero data (residual reads). Fix: drain + zero + controlled destination.

**Enforcement — machine-checkable.** A deterministic pattern flags this automatically in the [CLI](../../cli), the [GitHub Action](../../action.yml), the [Semgrep ruleset](../../semgrep), the [VS Code extension](../../extensions/vscode), and the [MCP server](../../mcp).

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the close= account that isn't fully drained/zeroed before close, or whose lamports go to an attacker-chosen destination.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the account is fully drained (lamports AND any token balances) before close and its data is zeroed, AND it holds no delegated authority over other on-chain resources (mints, PDAs, vaults) that must be explicitly revoked before close
2. the close destination is program-controlled or a signer-validated key, not an attacker-supplied account

## Real exploits in this class

No publicly catalogued exploit in the [Hacks Database](../../hacks/README.md) maps to this class yet. The rule is drawn from documented Solana audit patterns, not a specific in-the-wild loss.
