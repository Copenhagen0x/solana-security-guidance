# SOL-048 · Default/zero value accepted as valid

An authorization/membership gate trusts a stored field whose pre-init default is the zero value - `Pubkey::default()`, a `[0u8;32]` merkle/whitelist root, a zero nonce, or a freshly-`init`'d (zeroed) account - so the UNINITIALIZED state passes the check and an attacker submits a proof/key matching the zero sentinel (or beats the admin to the gate). On Solana an 8-byte discriminator proves the account was created, not that THIS field was set, so an `Account<T>` check does not rescue you. Distinct from SOL-010 (re-initializing an existing value). Fix: reject the zero sentinel at the gate (`require_keys_neq!(stored, Pubkey::default())`) and assert `is_initialized` on a bound config account

**Enforcement — review-only.** A judgment-call class with no deterministic pattern: it lives in the standard's review checklist and in your AI agent's [rules file](../../integrations), so the model reviews for it.

**Value tier — HIGH.** HIGH — high-value; surfaced even at a strict submission floor

**Baseline severity — high.** A starting point, not a verdict: calibrate by preconditions × access level (take the lower) per [SEVERITY.md](../../SEVERITY.md).

**Reachability anchor.** To confirm this is exploitable (not merely present), cite the authorization/membership gate (require_keys_eq! / require! / a manual `==` against a stored field) whose compared field has an all-zero default AND is reachable before that field is provably set to a non-default value on a canonical (PDA/singleton/address-bound) account — OR whose host account is attacker-substitutable (no seeds/has_one/address binding), so an attacker can supply their own config with the field set to a value they control.

**Do NOT flag when** — cite the number when suppressing a finding:

1. the gate compares against a field that is provably non-zero on a CANONICAL account before the comparison: (a) the host config/root account is bound by `seeds`/`bump`, `has_one`, or an explicit address check so it cannot be attacker-substituted, AND (b) an explicit `bool is_initialized` (or status enum) is asserted true, AND (c) the field was written in a verified-admin instruction to a value checked `!= the type's zero sentinel` at write time (`Pubkey::default()` for a Pubkey, `[0u8;32]` for a 32-byte root, `0` for a discriminator/nonce). A bare Anchor discriminator alone is NOT sufficient (it proves the account was created, not that THIS field was populated), and is_initialized==true on an UNBOUND account is NOT sufficient (Bring-Your-Own-Config still defeats the gate) — all three of (a),(b),(c) are required
2. the stored value being compared is a canonical hardcoded constant or a compile-time program id (never the zeroed default of a runtime-mutable account field), so no uninitialized or attacker-supplied state can ever reach the comparison
3. the zero/default value is explicitly rejected at the gate before any trust decision (`require_keys_neq!(stored, Pubkey::default())`, `require!(root != [0u8;32], ...)`, `require!(nonce != 0, ...)`, or a zero-sentinel routed exclusively to an UNAUTHORIZED/reject branch — a positive 'zero is denied' proof, not 'the default is probably never hit') AND the host account is canonical/bound (else the attacker just supplies a non-zero root on their own config)
4. the field is a pure non-security value (display label, free-form metadata) that never gates authorization, membership, fund movement, OR PDA/account derivation — proven by tracing every use-site, not 'this field looks cosmetic'. NOTE: a field consumed in PDA seed derivation IS a security input even if it reads as cosmetic (a metadata/label field reused as a seed is a trust input that selects which account/authority the gate resolves to), so this exclusion does NOT apply to any field that ever appears in a `seeds = [...]`
